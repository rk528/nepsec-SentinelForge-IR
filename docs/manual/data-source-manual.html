1. How log collection works

SentinelForge receives logs over HTTPS. Every log source posts batches of events to the ingestion API with its own secret key. The platform normalises the events, stores them, and immediately runs the detection rules over them.

FortiGatesyslog → relay
Windows serversPowerShell shipper
Microsoft 365Graph shipper / Logic App
Other systemsyour script → JSON API
→
Ingestion APIHTTPS POST
Authorization: Bearer sfk_…
One key per data source. Validates, normalises, de-duplicates.
→
SentinelForgeEvents stored → detection rules run → alerts in the queue → incidents, threat intel, response.

Key terms

TermMeaning
Data sourceA named log stream, for example “FortiGate HQ” or “DC01 Security log”. Each has a health status (Reporting / Stale), an event count and its own ingest key.
Ingest keyA secret starting with sfk_. It is shown once when created; only its hash is stored. It can only send events: it cannot read data or sign in.
Shipper / relayA small program that collects logs where they are produced and posts them to the API. SentinelForge provides ready-made ones for FortiGate, Windows and Microsoft Graph (folder connectors/ in the repository).
EndpointThe API address a shipper posts to. Each format has its own endpoint (table below).

2. Before you start

You need

  • A SentinelForge administrator account (only admins can create data sources and keys; demo accounts cannot).
  • For each source, a machine that can reach https://sentinelforge-api.kuinkel.com on TCP 443 (outbound HTTPS).
  • The connector scripts from the repository folder connectors/:
    • connectors/fortigate/fortigate_relay.py
    • connectors/windows/Send-WindowsEvents.ps1
    • connectors/microsoft-graph/ship_graph_logs.py
  • Python 3.10 or newer for the Python connectors (no extra packages). Windows PowerShell 5.1 or PowerShell 7 for the Windows shipper.

Check connectivity

From the machine that will run a shipper, the health check must return "status":"ok":

# Windows PowerShell
Invoke-RestMethod https://sentinelforge-api.kuinkel.com/api/v1/health

# Linux / macOS
curl -s https://sentinelforge-api.kuinkel.com/api/v1/health

If your network uses an outbound proxy, set HTTPS_PROXY for the Python connectors (they honour it) or use -Proxy with PowerShell.

Handling ingest keys safely

Treat every ingest key like a password.
  • Store it in an environment variable or a file readable only by the service account. Never put it on a command line, in a script, a ticket, chat or email.
  • Use one key per source so you can revoke one without affecting the others.
  • If a key may have leaked, Rotate it (Settings → Data sources). The old key stops working at once.

Free-tier capacity

The hosted database has 0.5 GB. Security events (logins, alerts, admin changes) are small and always worth sending. High-volume traffic logs are filtered by default in the FortiGate relay; keep the default unless you have a larger database.

Managing keys later

ButtonWhat it doesWhen to use it

Removing people instead of keys? Settings → Users and roles → Remove signs the person out everywhere and blocks sign-in while keeping their history. Ingest keys are not tied to people, so removing a user does not stop any shipper.

4. FortiGate firewall

FortiGate sends logs only as syslog. A small relay program inside your network receives the syslog and forwards it to SentinelForge over HTTPS.

FortiGateRemote logging: syslog to the relay, UDP or TCP port 5514
→
Relay machine (your LAN)fortigate_relay.py
Accepts only the firewall's IP, filters noise, batches every 5 s
→
SentinelForge/api/v1/ingest/fortigate

What is collected

SSL-VPN login failures and tunnels establishedLogin failure / successVPN password guessing (SF-AUTH-001)
Administrator logins to the firewallLogin failure / successSF-AUTH-001
Accepted traffic sessions (filtered)Network connectionSF-NET-001
DNS filter, web filterDNS query, web requestSF-MAIL-001

4.1 Create the data source

Follow chapter 3 with type fortigate (for example “FortiGate HQ”). Keep the sfk_ key ready.

4.2 Prepare the relay machine

Any always-on machine on the LAN that the FortiGate can reach: a small Linux VM, a Windows server, or a Raspberry Pi. Requirements: Python 3.10+, outbound HTTPS, and inbound UDP and TCP 5514 from the FortiGate.

Option A – Windows server

1

Install Python 3 from python.org (tick Add python.exe to PATH). Copy fortigate_relay.py to C:\SentinelForge\.

2

Allow the syslog port through Windows Firewall (PowerShell as Administrator; use your FortiGate's IP):

New-NetFirewallRule -DisplayName "SentinelForge relay UDP" -Direction Inbound -Protocol UDP -LocalPort 5514 -RemoteAddress 192.168.1.99 -Action Allow
New-NetFirewallRule -DisplayName "SentinelForge relay TCP" -Direction Inbound -Protocol TCP -LocalPort 5514 -RemoteAddress 192.168.1.99 -Action Allow
3

Store the settings as machine environment variables (not in the script):

[Environment]::SetEnvironmentVariable("SENTINELFORGE_URL", "https://sentinelforge-api.kuinkel.com", "Machine")
[Environment]::SetEnvironmentVariable("SENTINELFORGE_INGEST_KEY", "sfk_paste_your_key_here", "Machine")
4

Test it in a new PowerShell window; it should print Listening for FortiGate syslog…:

python C:\SentinelForge\fortigate_relay.py --allow 192.168.1.99
5

Run it permanently as a startup task (Administrator PowerShell):

$action  = New-ScheduledTaskAction -Execute "python.exe" -Argument "C:\SentinelForge\fortigate_relay.py --allow 192.168.1.99"
$trigger = New-ScheduledTaskTrigger -AtStartup
$settings = New-ScheduledTaskSettingsSet -RestartCount 999 -RestartInterval (New-TimeSpan -Minutes 1) -ExecutionTimeLimit ([TimeSpan]::Zero)
Register-ScheduledTask -TaskName "SentinelForge FortiGate relay" -Action $action -Trigger $trigger -Settings $settings -User "SYSTEM" -RunLevel Highest
Start-ScheduledTask -TaskName "SentinelForge FortiGate relay"

Option B – Linux (systemd)

sudo mkdir -p /opt/sentinelforge /etc/sentinelforge
sudo cp fortigate_relay.py /opt/sentinelforge/
sudo tee /etc/sentinelforge/relay.env >/dev/null <<'EOF'
SENTINELFORGE_URL=https://sentinelforge-api.kuinkel.com
SENTINELFORGE_INGEST_KEY=sfk_paste_your_key_here
EOF
sudo chmod 600 /etc/sentinelforge/relay.env

sudo tee /etc/systemd/system/sentinelforge-relay.service >/dev/null <<'EOF'
[Unit]
Description=SentinelForge FortiGate syslog relay
After=network-online.target
Wants=network-online.target

[Service]
EnvironmentFile=/etc/sentinelforge/relay.env
ExecStart=/usr/bin/python3 /opt/sentinelforge/fortigate_relay.py --allow 192.168.1.99
DynamicUser=yes
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now sentinelforge-relay
sudo journalctl -u sentinelforge-relay -f      # watch the log
sudo ufw allow from 192.168.1.99 to any port 5514   # if ufw is enabled

Relay options

OptionMeaning
--allow requiredComma-separated IPs of your FortiGate(s). Packets from any other address are dropped, so nobody can inject fake firewall logs.
--port 5514UDP and TCP port to listen on. 5514 avoids needing administrator rights for port 514.
--traffic interestinginteresting: only accepted sessions to public addresses on unusual ports or with more than 10 MiB sent. all: every session (very high volume). none: no traffic logs. VPN, admin, DNS, web filter and IPS logs are always sent.
--bind 0.0.0.0Local address to listen on; set the LAN IP to listen on one interface only.
--batch
--interval		Up to 200 lines per request, sent every 5 seconds.
--buffer 50000Lines kept in memory while SentinelForge is unreachable; the relay retries automatically.

4.3 Configure the FortiGate

Using the CLI (recommended)

Open the CLI console (top right in the GUI, or SSH) and run, replacing 192.168.1.50 with the relay machine's IP:

config log syslogd setting
    set status enable
    set server "192.168.1.50"
    set port 5514
    set mode udp                 # or "reliable" for TCP
    set format default           # "json" is also supported
    set facility local7
end

config log syslogd filter
    set severity information
    set forward-traffic enable
    set local-traffic disable
    set multicast-traffic disable
    set sniffer-traffic disable
    set anomaly enable
    set voip disable
end

If the FortiGate sends logs from a management interface or VDOM, pin the source address and put that same IP in the relay's --allow:

config log syslogd setting
    set source-ip 192.168.1.99
end

Using the GUI

  1. Log & Report → Log Settings → Remote Logging and Archiving.
  2. Enable Send logs to syslog and enter the relay's IP address. Click Apply.
  3. The GUI uses port 514 by default; set port 5514 and the mode with the CLI commands above.

4.4 Make sure the right events are logged

  1. Policy & Objects → Firewall Policy: open each Internet-facing policy and set Log Allowed Traffic to All Sessions (or at least Security Events).
  2. Security Profiles: in the DNS Filter, Web Filter and IPS profiles used by those policies, enable logging (for DNS filter: Log all DNS queries and responses).
  3. SSL-VPN logins and administrator logins are logged by default (Log & Report → Log Settings → Event Logging: VPN activity and System activity must be enabled).

4.5 Confirm

  1. On the FortiGate, check that packets leave towards the relay: diagnose sniffer packet any 'port 5514' 4 5.
  2. The relay prints statistics every 5 minutes, for example stats received=812, dropped_filter=640, sent=172, ….
  3. In SentinelForge, Settings → Data sources shows the FortiGate as Reporting; Events shows its records. Then run the safe test in chapter 10.

5. Windows servers and workstations

The PowerShell shipper runs every 5 minutes on each server (domain controllers first), reads the security-relevant event IDs since its last run, and posts them to SentinelForge.

Events collected

LogEvent IDsMeaning
Security4624, 4625Successful / failed logon (machine accounts and system logons are skipped)
Security4688Process created (with command line when enabled)
Security4720User account created
Security4728, 4732, 4756Member added to a global / local / universal security group
Security1102Security log cleared
System7036, 104Service stopped (e.g. Windows Event Log, Sysmon); log cleared
Sysmon1, 3, 22Process creation with hashes, network connection, DNS query (only if Sysmon is installed)

5.1 Turn on the required auditing

On a domain, set these in a GPO linked to servers and domain controllers: Computer Configuration → Policies → Windows Settings → Security Settings → Advanced Audit Policy Configuration. For a single machine, run in an Administrator command prompt:

auditpol /set /subcategory:"Logon" /success:enable /failure:enable
auditpol /set /subcategory:"Process Creation" /success:enable
auditpol /set /subcategory:"User Account Management" /success:enable /failure:enable
auditpol /set /subcategory:"Security Group Management" /success:enable
auditpol /set /subcategory:"Audit Policy Change" /success:enable

Include command lines in event 4688 (needed for suspicious-process detection). GPO: Administrative Templates → System → Audit Process Creation → Include command line in process creation events = Enabled, or on one machine:

reg add "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System\Audit" /v ProcessCreationIncludeCmdLine_Enabled /t REG_DWORD /d 1 /f
Optional: Sysmon adds file hashes, network connections and DNS queries per process. Install it from Microsoft Sysinternals with a community configuration (for example SwiftOnSecurity's) — the shipper picks it up automatically.

5.2 Install the shipper

1

Create a data source (chapter 3), type windows_security, one per server or one shared by a group of servers.

2

Copy Send-WindowsEvents.ps1 to C:\SentinelForge\ on the server.

3

Store the key at machine level (Administrator PowerShell):

[Environment]::SetEnvironmentVariable("SENTINELFORGE_INGEST_KEY", "sfk_paste_your_key_here", "Machine")
4

Run it once by hand to test (Administrator PowerShell, because the Security log requires it):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\SentinelForge\Send-WindowsEvents.ps1 -ApiUrl https://sentinelforge-api.kuinkel.com

Expected output: … sent 214 events, 214 new, 0 alerts raised. The first run reads the last 60 minutes (-LookbackMinutes changes this).

5

Schedule it every 5 minutes as SYSTEM:

$action  = New-ScheduledTaskAction -Execute "powershell.exe" -Argument '-NoProfile -ExecutionPolicy Bypass -File "C:\SentinelForge\Send-WindowsEvents.ps1" -ApiUrl https://sentinelforge-api.kuinkel.com'
$trigger = New-ScheduledTaskTrigger -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Minutes 5)
Register-ScheduledTask -TaskName "SentinelForge event shipper" -Action $action -Trigger $trigger -User "SYSTEM" -RunLevel Highest

6. Microsoft Entra ID and Microsoft Defender

The Graph shipper reads Entra ID sign-in and audit logs and Defender XDR alerts from Microsoft Graph using an app registration, and posts them to SentinelForge. Run it on any always-on machine with outbound HTTPS.

StreamGraph sourcePermissionLicence
entra-signin/auditLogs/signInsAuditLog.Read.All, Directory.Read.AllEntra ID P1 or P2
entra-audit/auditLogs/directoryAuditsAuditLog.Read.AllAny
defender-alert/security/alerts_v2SecurityAlert.Read.AllDefender for Endpoint / Office 365 / Identity, or Microsoft 365 E5 / Business Premium
MFA prompts are not failures. Sign-in records that only asked for MFA, "Stay signed in?" or a password change are skipped, so normal MFA use never looks like password guessing.

6.1 Register the application

1

Open entra.microsoft.com as a Global Administrator or Privileged Role Administrator → Applications → App registrations → New registration. Name: SentinelForge log shipper; Accounts in this organizational directory only; no redirect URI. Click Register.

2

On the Overview page copy the Directory (tenant) ID and Application (client) ID.

3

API permissions → Add a permission → Microsoft Graph → Application permissions. Add AuditLog.Read.All, Directory.Read.All and SecurityAlert.Read.All. Then click Grant admin consent for <your tenant>; every permission must show a green tick.

4

Certificates & secrets → Client secrets → New client secret, expiry 6–12 months. Copy the secret Value immediately (it is hidden afterwards). Put a reminder in your calendar to renew it before it expires.

6.2 Create data sources

Create one source of type microsoft_entra (sign-ins and audit) — and optionally a separate microsoft_defender source if you want separate health tracking. One key can serve all three streams.

7. Azure Monitor, Log Analytics and Microsoft Sentinel

If your logs already flow into a Log Analytics workspace (Microsoft Sentinel, Defender for Cloud, Azure Monitor Agent), you can forward them without running anything on your servers, using a Logic App.

7.1 Store the ingest key in Key Vault

  1. Create a data source in SentinelForge (chapter 3) and copy the key.
  2. In the Azure portal open (or create) a Key Vault → Secrets → Generate/Import, name sentinelforge-ingest-key, value = the key.

7.2 Build the Logic App

1

Create a Logic App (Consumption). Under Identity enable the system-assigned managed identity, and give it Log Analytics Reader on the workspace and Key Vault Secrets User on the vault.

2

Trigger: Recurrence, every 5 minutes.

3

Action: Azure Monitor Logs → Run query and list results on your workspace with one of these queries (time range: last 5 minutes):

// Windows security events  → endpoint .../ingest/microsoft/windows-event
SecurityEvent
| where EventID in (4624, 4625, 4688, 4720, 4728, 4732, 4756, 1102)
| project TimeGenerated, Computer, EventID, EventData

// Entra ID sign-ins → .../ingest/microsoft/entra-signin
SigninLogs
| project TimeGenerated, UserPrincipalName, IPAddress, ResultType, ResultDescription, AppDisplayName, LocationDetails, DeviceDetail

// Entra ID audit → .../ingest/microsoft/entra-audit
AuditLogs
| where OperationName in ("Add user", "Add member to role", "Add member to group", "Add eligible member to role")
| project TimeGenerated, OperationName, Result, InitiatedBy, TargetResources

// Security alerts → .../ingest/microsoft/defender-alert
SecurityAlert
| project TimeGenerated, AlertName, AlertSeverity, ProviderName, CompromisedEntity, Description
4

Action: Azure Key Vault → Get secret sentinelforge-ingest-key. In its Settings, turn on Secure outputs so the key never appears in run history.

5

Action: HTTP

Method
POST
URI
https://sentinelforge-api.kuinkel.com/api/v1/ingest/microsoft/windows-event (or the endpoint matching the query)
Headers
Authorization: Bearer @{body('Get_secret')?['value']}
Content-Type: application/json
Body
@{body('Run_query_and_list_results')?['value']}

Turn on Secure inputs for this action as well. If more than 500 rows can arrive in 5 minutes, run the trigger more often or add a Chunk step (batches of 500).

6

Save, click Run, and check the HTTP action's output: {"received": …, "inserted": …, "skipped": …}.

8. Any other source: the JSON ingestion API

Anything that can make an HTTPS request — a Linux server script, a SaaS webhook, a SIEM export, an EDR — can send events directly in SentinelForge's normalised format.

Request

POST https://sentinelforge-api.kuinkel.com/api/v1/ingest/events
Authorization: Bearer sfk_...
Content-Type: application/json

{
  "events": [
    {
      "event_time": "2026-10-27T09:15:00Z",
      "event_type": "auth.failure",
      "host": "web-01",
      "user_name": "j.doe",
      "src_ip": "203.0.113.45",
      "outcome": "failure",
      "message": "sshd: Failed password for j.doe",
      "raw": {"program": "sshd", "pid": 4123}
    }
  ],
  "run_detection": true
}

Response: {"received": 1, "inserted": 1, "duplicates": 0, "alerts_created": 0, "alerts_updated": 0, "skipped": 0}

Examples

curl (Linux / macOS)

curl -sS -X POST https://sentinelforge-api.kuinkel.com/api/v1/ingest/events \
  -H "Authorization: Bearer $SENTINELFORGE_INGEST_KEY" -H "Content-Type: application/json" \
  -d '{"events":[{"event_time":"2026-10-27T09:15:00Z","event_type":"auth.failure","host":"web-01","user_name":"j.doe","src_ip":"203.0.113.45"}]}'

PowerShell

$body = @{ events = @(@{ event_time = (Get-Date).ToUniversalTime().ToString("o"); event_type = "auth.failure"
                         host = "web-01"; user_name = "j.doe"; src_ip = "203.0.113.45" }) } | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -Uri https://sentinelforge-api.kuinkel.com/api/v1/ingest/events `
  -Headers @{ Authorization = "Bearer $env:SENTINELFORGE_INGEST_KEY" } -ContentType "application/json" -Body $body

Python

import os, json, urllib.request, datetime
event = {"event_time": datetime.datetime.now(datetime.UTC).isoformat(), "event_type": "auth.failure",
         "host": "web-01", "user_name": "j.doe", "src_ip": "203.0.113.45"}
req = urllib.request.Request("https://sentinelforge-api.kuinkel.com/api/v1/ingest/events",
    data=json.dumps({"events": [event]}).encode(), method="POST",
    headers={"Authorization": f"Bearer {os.environ['SENTINELFORGE_INGEST_KEY']}", "Content-Type": "application/json"})
print(urllib.request.urlopen(req, timeout=30).read().decode())

Rules

  • 1–500 events per request, body up to 1 MiB, at most 60 requests per minute per data source.
  • event_time must include a time zone (e.g. Z) and may not be more than 5 minutes in the future.
  • Unknown fields are rejected; put extra vendor data in raw (any JSON object).
  • Sending the same event twice is harmless: duplicates are detected and ignored.

12. Security checklist and reference

Security checklist

  • One data source and key per log sender.
  • Keys stored only in environment variables, protected files (chmod 600) or Key Vault.
  • FortiGate relay restricted with --allow and a host firewall rule.
  • Shippers run as SYSTEM / a dedicated service account, not a personal account.
  • Graph app registration has only the three read permissions; secret expiry tracked.
  • Keys rotated at least yearly and whenever staff with access leave.
  • Unused sources revoked; mistaken ones deleted.
  • Former staff removed under Settings → Users and roles.
  • Provider keys (NepSec Intel, VirusTotal…) only in Vercel as Sensitive.
